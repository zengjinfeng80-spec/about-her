# Gemini 免费额度接入设计

## 目标

将“雪梨”的文字、图片、录音分析和“问记录”从 OpenAI API 切换到 Gemini API 免费额度，保持现有数据结构、证据约束、隐私隔离和用户界面不变。

成功标准：

- 文字、图片和录音记录都能完成分析。
- “问记录”只根据已保存证据回答并返回有效引用。
- 分析失败不会丢失原始记录，且界面显示可操作的中文原因。
- Gemini 密钥仅存在 Supabase Edge Function Secrets，不进入前端包、Git 或 GitHub Actions 日志。
- 全部自动化测试、生产构建、Edge Function 真实请求和线上验收通过。

## 范围与边界

- 本次只更换 AI 供应商及直接相关的错误展示。
- 不改动 Supabase Auth、RLS、数据表、私有存储、分析任务幂等或 GitHub Pages 部署模式。
- 不增加 OpenAI 自动备用、多供应商路由或前端模型选择器。
- 免费额度不等于永久免费。遇到供应商限额时，应保留记录并允许稍后重试，不自动切换到付费服务。
- 用户已确认：分析时可以将相关文字、图片和录音发送给 Google Gemini 处理。

## 服务端设计

### Gemini 适配器

用 `supabase/functions/_shared/gemini.ts` 取代当前 OpenAI 适配器，对 Edge Function 暴露两个稳定能力：

- `structuredResponse`：接收指令、文字和媒体，请求 Gemini 返回结构化 JSON。
- `transcribeAudio`：将一段录音转写为文字，不归纳、改写或推测。

服务端变量保持按任务分开：

- `GEMINI_API_KEY`
- `GEMINI_ANALYSIS_MODEL`
- `GEMINI_ASK_MODEL`
- `GEMINI_TRANSCRIPTION_MODEL`

模型名不写死在代码中。当前网络无法稳定读取 Google 官方文档，因此在取得 Gemini Key 后，必须通过 Google 官方模型列表与最小真实请求确认免费额度、输入模态和结构化输出能力，再写入 Supabase Secrets。

### 媒体处理

`analyze-entry` 继续从 `memory-media` 私有桶中读取文件，但不向 Gemini 暴露 Supabase 签名 URL。

- 纯文字直接进入生成请求。
- 图片和录音由 Edge Function 下载后提交给 Gemini。
- 超过 Gemini 内联请求限制的媒体使用 Gemini 文件接口临时上传。
- 临时文件在请求的 `finally` 阶段尝试删除；清理失败不覆盖主分析结果，但需记录可诊断信息。
- 现有“最多 4 张图片、一段 5 分钟录音、单文件 25 MB”产品限制保持不变。

### 结构化输出

分析和问答继续使用现有 JSON 契约。Gemini 返回后仍必须通过本地解析器和引用存在性检查；即使供应商声称支持结构化输出，也不直接信任其结果。

保留以下规则：

- 只输出六个现有分类。
- 区分 `explicit` 与 `inferred`。
- 证据摘录必须来自原文、转写或图片可见文字。
- 不根据表情、长相、姿态推断性格、感情、态度或关系。
- “问记录”引用的 `claimId` 和 `entryId` 必须存在于当前用户的可用数据中。

## 错误与重试

- 密钥或模型变量缺失：明确提示服务端配置未完成。
- 免费额度或频率限制：保留失败任务，提示稍后重试，不循环自动重试。
- 超时、上游 5xx 或网络失败：记录可诊断原因，原始记录继续可见，由用户触发现有的重新分析。
- 无效 JSON、无效分类或虚假引用：视为分析失败，不写入候选档案。
- 前端调用 Edge Function 失败时，优先解析服务端返回的 `{ error }`，避免只显示“返回非 2xx”的笼统错误。

## 测试与验收

### 自动化测试

- Gemini 请求构造：纯文字、图片、录音和结构化输出配置。
- Gemini 返回解析：正常 JSON、空候选、缺失文本、无效 JSON 和安全拦截。
- 服务错误：密钥缺失、模型缺失、429、5xx 和超时。
- 媒体处理：MIME 类型、内联与临时文件路径、临时文件清理。
- 前端错误：能显示服务端返回的中文原因，并保留无法解析时的通用兜底。
- 原有分类、推测确认、证据、媒体和账号隔离测试全部继续通过。

### 真实验收

1. 用新记录验证纯文字分析和证据摘录。
2. 用含可见文字的图片验证客观识别，确认不产生外貌或关系推断。
3. 用一段短录音验证转写、分析和证据回溯。
4. 对已完成分析的记录提问，验证回答与引用；再提一个证据不足的问题，验证明确拒答。
5. 人为使用无效模型名或受控测试环境验证错误文案与重新分析。
6. 检查 Supabase Function 日志不包含 API Key、原始媒体或完整私密记录。
7. 确认 GitHub Actions 成功，生产 URL 返回 HTTP 200，线上登录后功能与本地验收结果一致。

## 部署顺序

1. 完成适配器、Edge Function 和前端错误解析改动。
2. 通过自动化测试与生产构建。
3. 在 Google AI Studio 创建 Gemini API Key。密钥不在聊天中传输，由用户在本机或 Supabase Secrets 界面安全填入。
4. 用官方模型列表和最小请求确认可用模型，配置四个 Gemini 变量。
5. 部署 `analyze-entry` 和 `ask-memory`，完成真实验收。
6. 如前端错误显示有改动，提交并推送 `main`，等待 GitHub Pages 工作流完成后验证线上版本。
